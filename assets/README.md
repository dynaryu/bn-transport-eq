# Asset registry

One declaration per knowledge asset, and every declaration signs the same contract:
the `cap:` vocabulary in [`ontology/capabilities.ttl`](../ontology/capabilities.ttl).
An asset takes one of two forms.

**A folder asset** is a model with code of its own. It has five parts:

```
<category>/<asset-name>/
├─ asset.ttl     # the contract: target, parents, state spaces, capabilities
├─ README.md     # what it maps, why each capability holds, assumptions
├─ SOURCE.md     # citation, development background, licence, retrieval date
├─ model.py      # the wrapper, implementing exactly what asset.ttl declares
├─ params/       # the numbers, separate from the code that uses them
└─ tests/        # known-value regression
```

**A single-file asset** is one model among many that share a wrapper — one
fragility class, one ground-motion family. Its contract, provenance and numbers are
all in one JSON file, so it can be contributed, reviewed and withdrawn without
touching its neighbours:

```
<category>/<collection>/
├─ <name>.asset.json   # one asset: contract + provenance + numbers
├─ <name>.asset.json   # ... one file per asset
├─ model.py            # the wrapper they share, named by each file's implementedBy
├─ README.md  SOURCE.md
└─ tests/
```

This is the form a registry fed by many contributors takes, and the fragility and
ground-motion collections are kept this way to exercise it:

| Collection | Files | Each file is |
|---|---|---|
| `fragility/hazus-bridge/` | 28 | one Hazus bridge class, `HWB1` … `HWB28` |
| `fragility/hazus-roadway/` | 2 | one Hazus roadway class, `HRD1`, `HRD2` |
| `hazard/gmpe/` | 30 | one published ground-motion model family |

**The declaration is the contract, `model.py` must satisfy it, `tests/` proves it.**
Without the third the registry rots quietly: a wrapper claims `EvaluateDensity`
because the source paper describes a density, nobody checks, the compiler selects
MCMC, and the failure appears as poor mixing rather than as an error.

So before trusting the registry:

```bash
python -m src.conformance.check
```

It calls every declared capability on every asset and reports three things:

- **OVERCLAIM** — declared but missing, or present and raising. Correctness bug.
- **underclaim** — implemented but not declared. Harmless, but the compiler will
  never choose it.
- **BROKEN** — the asset would not load, or its file departs from the schema.

It checks the **contract against the wrapper**. Whether an asset has the *numbers*
it needs is a separate question with its own answer: a wrapper that refuses to
construct for want of data raises `DataUnavailable`, and the harness prints `data`
rather than `ok`. That state conforms only if the declaration claims no capability
— claiming one is an overclaim like any other. `hazard/gmpe` is the live example:
30 families registered, 30 files with `"hasCapability": []`, none able to predict.

## Single-file assets

The file is one JSON object whose keys are the local names of the properties the
ontology gives `cap:Asset` — `assetId`, `implementedBy`, `targetVariable`,
`hasCapability`, `validityScope` and so on — plus two that hold what a folder asset
keeps beside its `asset.ttl`:

| Key | Holds | Folder-asset equivalent |
|---|---|---|
| `source` | citation, table, retrieval date, verification level | `SOURCE.md` |
| `parameters` | the numbers, in whatever structure the wrapper reads | `params/` |

**The schema is derived from the ontology, not written beside it.**
`ontology/asset.schema.json` is generated by

```bash
python -m src.conformance.schema          # rewrite it after editing capabilities.ttl
python -m src.conformance.schema --check  # fail if it is stale
```

from three things the ontology states: which properties have `cap:Asset` as their
domain (the keys), each property's range (the type, or the permitted values where
the range is a class of named individuals), and the cardinality restrictions on
`cap:Asset` (one value or a list; required or optional). To add a contract field,
add it to the ontology and regenerate — a key the ontology does not define is
refused, so a file cannot carry a field no compiler reads.

Rules the harness enforces on every `*.asset.json`:

- It observes the derived schema. This is checked before anything is loaded or run.
- `assetId` is `<category>/<collection>/<name>`, where `<name>` is the file name
  without `.asset.json`. Deriving the id from the location is what keeps two
  contributed files from claiming one identity.
- `implementedBy` resolves against the file's own folder, and the wrapper is bound
  to that file with `from_asset_file()`. The smoke test therefore exercises the asset
  declared, not whichever one the wrapper defaults to.
- `hasCapability` lists only what runs for *this* asset. An empty list is a valid,
  honest declaration.

Only the `.asset.json` suffix marks a declaration. A bare `*.json` under `assets/`
is a parameter table or a fixture and is never picked up as an asset.

**To contribute one:** copy
[`_template/template.asset.json`](_template/template.asset.json) into the
collection whose wrapper reads your numbers, name it for the asset, fill every
field, and run the conformance check. Start the file with
`"$schema": "../../../ontology/asset.schema.json"` and an editor will flag a
misspelt key or a missing field as you type. A model that needs code of its own is a
folder asset: start from the rest of [`_template/`](_template/).

## Categories

| Category | Supplies |
|---|---|
| `hazard/` | `HazardEvent` → `LocalIntensity` |
| `fragility/` | `LocalIntensity`, `AssetHealth` → `AssetDamageState` |
| `deterioration/` | `AssetHealth` over time |
| `ds-to-functional/` | `AssetDamageState` → `AssetFunctionality` |
| `system/` | `AssetFunctionality` → `Service` |

`ds-to-functional/` is a first-class category on purpose. It is usually buried
inside a fragility implementation or a simulator, and that is exactly why damage
state vocabularies silently fail to line up between asset types. Giving it its
own assets with declared state spaces forces the mismatch into the open, where
the conformance check can see it.

## Naming

`fragility/hazus-roadway/` and `fragility/hazus-bridge/` provide the supplied Hazus
6.1 earthquake curves, one asset file per class. They use distinct four-state and
five-state damage spaces; none declares an AssetHealth parent. See
[the guide](../docs/hazus61-fragility.md) before connecting any of them to
deterioration or damage-to-functionality assets.

The system registry includes `global-connectivity`, `travel-time`,
`population-accessibility`, and `staged-max-flow` adapters for the local ndtools
checkout. See [network simulators](../docs/network-simulators.md) for setup and
their shared `component-ratios-v1` input contract. `cap:serviceMetric` distinguishes
these meanings of Service so the pilot selects an appropriate factor.

Folder names are free — wrappers load by file path, not module name, so hyphens
are fine. Keep `cap:assetId` equal to `<category>/<folder>` for a folder asset; for
a single-file asset it is `<category>/<folder>/<name>`, and the harness checks it.

Folders named `_pending` hold a `SOURCE.md` stating what is still needed. Replace
them with real assets as the sources land; do not fill them with placeholder
numbers.
